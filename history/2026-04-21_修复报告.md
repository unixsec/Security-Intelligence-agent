# Security Intelligence Agent 代码审查与修复报告

- **日期**：2026-04-21
- **审查范围**：`src/sia/` 下全部 Python 源码（约 5,800 行）、`config/`、`pyproject.toml`
- **修复文件总数**：13
- **新增依赖**：1（`aiosmtplib>=3.0.0`）

---

## 一、总体结论

项目整体架构清晰（FastAPI + SQLAlchemy 2 async + Redis Streams + LLM Gateway + APScheduler），分层合理。但存在若干会**直接影响运行时行为和安全性**的缺陷，主要集中在：

1. 认证路径中的事务回滚导致防暴破机制失效；
2. 数据脱敏模块在多规则串行匹配时会损坏已产生的占位符；
3. LLM token 账单丢失精度；
4. 邮件推送缺少运行时依赖；
5. LDAP StartTLS 协商时机错误，存在明文传输风险；
6. API schema 与数据库 JSON 字段形态不匹配，会造成接口反序列化失败。

以下按严重级别列出每个问题及修复方案。

## 二、严重 Bug 修复（会直接导致错误行为 / 安全问题）

### 1. 登录失败计数被事务回滚 —— 可被无限爆破

- **文件**：`src/sia/gateway/api/v1/auth.py`
- **位置**：本地登录分支 `login()`
- **问题**：
  - 密码错误时代码递增 `user.failed_login_count`，达到阈值则锁定账号；随后 `raise HTTPException(401)`。
  - `get_db()` 依赖在异常路径下会 `session.rollback()`，导致刚刚的自增与锁定全部被撤销。
  - **后果**：暴破保护完全失效，攻击者可无限次尝试密码。
- **修复**：在 `raise` 之前显式 `await db.commit()`，持久化失败计数与锁定时间。
- **提交内容（节选）**：

```python
if not user.hashed_password or not verify_password(body.password, user.hashed_password):
    user.failed_login_count += 1
    if user.failed_login_count >= max_attempts:
        user.status = "locked"
        user.locked_until = datetime.now(timezone.utc) + timedelta(
            minutes=lockout_cfg.get("lockout_duration_minutes", 30)
        )
    await db.commit()   # ← 新增：提前提交，防止异常回滚
    raise HTTPException(status_code=401, detail="Invalid username or password")
```

### 2. 脱敏模块占位符被后续规则二次匹配，导致脱敏结果损坏

- **文件**：`src/sia/gateway/llm/anonymizer.py`
- **位置**：`DataAnonymizer._anonymize_text`
- **问题**：
  - 原逻辑对每条正则都在已替换过的 `result` 上调用 `finditer`；某条规则可能命中上一条规则刚写入的占位符（例如 `[INTERNAL_IP_abc123]` 中的英文片段），**再次替换会破坏占位符，使 `deanonymize` 无法还原**。
  - 另外 `for original, placeholder in ctx.reverse.items()` 每轮都把完整映射重放一次，O(n²) 冗余工作。
- **修复**：改为**单趟扫描**：先收集所有规则在**原文本**上的候选区间，按起点排序 + 长区间优先 + 丢弃重叠区间，再一次性按位置拼接输出。保证：
  - 占位符内部字符不再被后续规则二次匹配；
  - 同一原文共享同一占位符；
  - 无重复替换。

### 3. LLM token 统计精度丢失（账单 / 配额不准确）

- **文件**：
  - `src/sia/gateway/workflow/steps/llm_call.py`
  - `src/sia/analyzer/pipeline.py`
- **问题**：
  - `llm_call` 只把 `response.total_tokens` 写入 ctx 元数据；
  - `pipeline.persist_analysis_result` 中使用 `meta.get("tokens", 0) // 2` 平均拆分输入/输出 token。
  - 所有 provider 实际上都返回 `input_tokens` 与 `output_tokens`，`LLMResponse` 也有这两个字段，**强行对半拆分使成本计量与配额控制失真**。
- **修复**：
  - `llm_call.py` 中把 `input_tokens` / `output_tokens` / `total_tokens` 一并放入 ctx；
  - `pipeline.py` 优先使用 provider 上报的拆分值，仅在两者都缺失时回退到平均拆分（此时兜底用 `total - input_tokens` 保证总和一致）。

### 4. 邮件推送通道缺少 `aiosmtplib` 依赖

- **文件**：`src/sia/reporter/pusher/channels.py`、`pyproject.toml`
- **问题**：`EmailChannel.send()` 中 `import aiosmtplib`，但 `pyproject.toml` 未声明该依赖。**生产环境首次发邮件时 `ImportError`**。
- **修复**：`pyproject.toml` 的 `dependencies` 新增 `aiosmtplib>=3.0.0`。

### 5. LDAP StartTLS 时机错误，绑定密码明文传输

- **文件**：`src/sia/auth/providers/ldap.py`
- **问题**：
  - 服务账号 `Connection(..., auto_bind=True)` 会先发送 bind 请求再尝试 `start_tls()`；服务账号口令此时已经**以明文越过传输层**。
  - 用户二次绑定同样只用 `auto_bind=True`，完全没有 StartTLS 升级。
- **修复**：
  - 两处都改为 `auto_bind=False`；
  - 先 `start_tls()` 协商，失败则抛异常；
  - 再调用 `bind()`；
  - 用户鉴权流程同样应用 StartTLS，使密码始终在 TLS 之内。

### 6. Schema 与数据库 JSON 字段形态不匹配

- **文件**：`src/sia/gateway/api/schemas.py`
- **问题**：
  - `Intelligence.tags` / `mitre_tactics` / `mitre_techniques` 数据库字段是 JSON（实际 LLM 可能返回字典也可能返回列表）；
  - Schema 声明为 `list[str] | None`，**遇到 dict 形态即 Pydantic 校验失败**，详情接口 500。
  - 另外 `IntelligenceDetail` 继承自 `IntelligenceListItem` 却重复声明了 `cve_id` 字段。
- **修复**：
  - 三个字段放宽为 `list[str] | dict[str, Any] | None`；
  - 删除重复的 `cve_id`。

## 三、安全 / 设计问题修复

### 7. OIDC 回调错误信息泄露

- **文件**：`src/sia/gateway/api/v1/auth.py`
- **问题**：`detail=f"OIDC authentication failed: {e}"` 把内部异常（可能含 IdP URL、token endpoint 细节）回显给客户端。
- **修复**：仅记录 `logger.exception`，对外返回通用信息 `"OIDC authentication failed"`。

### 8. 硬编码 Dev API Key

- **文件**：`src/sia/auth/rbac.py`
- **问题**：未配置 `SIA_API_KEY` 时回退为字面量 `"dev-key-not-for-production"`，任何知道该字符串的人都能通过鉴权；同时还有一份内嵌进函数体的 `import os / secrets / get_settings`。
- **修复**：
  - 删除字面量兜底，未配置时直接返回 401；
  - 把 `os` / `secrets` / `get_settings` 提升到模块顶部；
  - 保留 dev 模式下匿名访问分支（`env == "dev"`）。

### 9. 限流中间件健康检查白名单脆弱

- **文件**：`src/sia/gateway/api/rate_limit.py`
- **问题**：`request.url.path.endswith("/health")` 对路径 `/foo/bar/health` 也成立，容易被绕过。
- **修复**：改为明确路径集合 `{"/health", "/healthz", "/api/v1/health", "/api/health"}`，并对尾部斜杠进行归一化。

### 10. CircuitBreaker 声称使用 asyncio.Lock 但从未加锁

- **文件**：`src/sia/gateway/llm/circuit_breaker.py`
- **问题**：`_lock` 字段存在但从未 `async with`；`record_success` / `record_failure` 内有未使用变量 `prev = self.state`，误导审查者。
- **修复**：删除 `_lock` 字段，移除无效 `prev`，把 docstring 改为"单事件循环天然串行，无需显式锁"。

## 四、架构一致性修复

### 11. User/RefreshToken 未注册到 `models/__init__.py`

- **文件**：`src/sia/models/__init__.py`、`src/sia/common/database.py`
- **问题**：
  - `init_db()` 仅依赖先前被 import 的模型模块注册到 `Base.metadata`；
  - 如果 `init_db()` 在路由加载前运行（dev/test 下确实有这种路径），`users` / `refresh_tokens` 表不会被建出来；
  - `models/__init__.py` 也没有导出 `User` / `RefreshToken`。
- **修复**：
  - `models/__init__.py` 显式导入并加入 `__all__`；
  - `init_db()` 内加上 `import sia.models` 侧效用导入，确保任何调用路径下 metadata 都是完整的。

### 12. `job_reload_prompts` 是死代码仍被每 5 分钟调度

- **文件**：`src/sia/scheduler/service.py`、`src/sia/scheduler/jobs.py`
- **问题**：
  - PromptManager 是**每个消费者协程内部自行实例化**的（见 `analyzer/pipeline.run_analysis_consumer`），从调度器进程调用无法刷新任何已存在的 PromptManager；
  - 原实现直接写了 no-op，还每 5 分钟执行一次并打一条"hot-reload triggered"日志，属于误导性日志噪音。
- **修复**：
  - 从调度器里彻底移除该 job；
  - 保留 `job_reload_prompts` 函数供 `/api/v1/system/reload-prompts` 手动触发，但 docstring 与日志诚实说明"仅为信号接受，真正刷新需消费者自身周期"。

## 六、建议的后续跟进项（本轮未做，列为 backlog）

以下项目非紧急但建议后续处理：

1. **分布式部署下的 token bucket 限流**：目前 `RateLimitMiddleware` 是进程内内存字典，多 Pod 下不共享。建议迁移到 Redis。
2. **API Key RBAC 细化**：当前 API Key 恒等于 admin，应支持 per-key 角色。
3. **Milvus 降级策略**：`analyzer/dedup.py` 在 Milvus 不可用时静默返回空列表，生产环境应当至少打 metric / alert。
4. **SSRF 校验**：`schemas.SourceCreate.validate_url` 目前能防大多数场景，但未覆盖 IPv6 loopback `[::1]:port` / 云 metadata `169.254.169.254` 等边缘形态，可替换为 `ipaddress` 全量判断。
5. **时间戳时区一致性**：`models/user.py` 的 `locked_until` 是 naive `DateTime`，但代码写入时用 `datetime.now(timezone.utc)`，依赖调用侧做 `.replace(tzinfo=…)`。建议统一为 `DateTime(timezone=True)`。
6. **报告生成未接 LLM**：`gateway/api/v1/reports.py` 和 `scheduler/jobs.py` 中的 `generate_report` / `job_daily_report` 目前只是字符串拼接，未真正通过 `WorkflowEngine` 触发 LLM 报告生成流程。
7. **`sources.py` 创建后仅 flush**：依赖 `get_db` 最后提交，逻辑正确但不够显式，建议显式 commit 便于排查。
